### What this PR does / why we need it?

Batches the sinkhorn iterations of the `hc_pre` comb stage (A3 vector path).

Each token carries a 4x4 comb matrix that goes through 20 rounds of row/column
normalization. The matrix is 16 floats — smaller than what one vector instruction
processes per repeat — so the baseline pays pure issue overhead: ~190 instructions
per token, most of them `mask=4` adds issued from a per-token loop.

- `hc_pre_base.h`: three batched column helpers (`ColSumBlockRowBatch`,
  `AddEpsColSumBatch`, `ColDivBlockRowBatch`) plus a `SinkhornColStage` entry.
  They keep the per-token `[hcMult rows][one block]` layout and open the repeat
  over tokens, so one column stage costs O(1) instructions regardless of how many
  tokens are staged. Accumulation order matches `ReduceSumARAPerf`, so results are
  bit-identical to the per-token path. Also fixes the column-sum epsilon, which a
  contiguous `Adds` count applied to only the first half of the tokens.
- `hc_pre_m_k_split_core.h`: stage 2 keeps the init (softmax + first column
  normalization) in the per-row loop so it still overlaps the x/y copies, writes
  it into a staging tensor, and once `combRowFactor` rows are staged runs the
  remaining iterations in place over the whole group and flushes through the
  VECOUT queue. Also drops a duplicated `squareSumQue` `InitBuffer`.
- `hc_pre_tiling.{h,cpp}`: `combRowFactor` becomes a tiling field. The host sizes
  it against the real UB budget (`CalcStage2UbSize` mirrors the kernel's
  `InitBuffer` list one for one) and grows it in whole `stage2RowFactor` groups,
  so `stagedRows` lands on the bound exactly instead of stepping over it. It comes
  out 32 for large batches and 1 for decode, where the footprint is then identical
  to the unbatched kernel. An `hc_mult == 4` precondition check replaces a kernel
  fallback branch that could never run.

Perf, kernel-level microbench on Ascend 910C (us, baseline -> optimized):

| bs | d=4096 | d=7168 |
|---|---|---|
| 2 | 32.3 -> 30.6 (noise) | 35.0 -> 34.4 (noise) |
| 16 | 33.5 -> 32.6 (noise) | 36.3 -> 35.8 (noise) |
| 256 | 83.4 -> 71.9 (-13.8%) | 96.6 -> 84.1 (-12.9%) |
| 512 | 128.4 -> 99.0 (-22.9%) | 151.0 -> 121.6 (-19.5%) |
| 1024 | 206.4 -> 147.2 (-28.7%) | 249.9 -> 193.8 (-22.4%) |
| 1536 | 279.7 -> 195.5 (-30.1%) | 345.7 -> 264.3 (-23.5%) |
| 2100 | 389.2 -> 277.9 (-28.6%) | 508.4 -> 388.0 (-23.7%) |
| 8192 | 1354.6 -> 910.7 (-32.8%) | 1727.1 -> 1318.6 (-23.7%) |

Small batches take the unbatched path (`combRowFactor = 1`) by design; the
absolute saving is d-independent (~410-440 us at bs=8192), matching the fact that
comb work scales with token count only.

### Does this PR introduce _any_ user-facing change?

No. Kernel-internal optimization: operator API, tiling ABI, workspace contract and
output semantics are unchanged.

### How was this patch tested?

- microbench A/B above on 910C (final code)
- batched path cross-checked against the unbatched path: bit-identical outputs
