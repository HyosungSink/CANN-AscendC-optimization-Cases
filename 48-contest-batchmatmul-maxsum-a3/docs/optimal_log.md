# BatchMatmulMaxSum 优化记录

测量口径：远端 CANN 9.0.0、`msprof` 的单次 NPU `Task Duration(us)`；不是 OJ 隐藏 case 的用时。基线提交：`8544f0a`。

## 2026-09-23：形状驱动的切分与多核归约

- 按 `M/N` 选 `tileM=64/128`、`tileN=64/128/256`，避免小矩阵仍分配完整的 `128×256` UB/GM 块。仅当 `K≥256` 且 M 方向并行不足时考虑较小的 M 块；`M=512,N=2048,K=128` 上，`tileM=64` 为 122.6 μs，慢于 `tileM=128` 的 102.2 μs，因此不对低 K 使用。
- 对短 M、宽 N 且 M 方向核数不足的形状，把 N tile 分给不同核；各核写连续的局部行最大值，单个 AIV 同步屏障后按 batch 合并。`M=64,N=4096,K=128` 从 1 核/82.8 μs 变为 16 核/23.8 μs。
- 对 `M=512,N=2048,K=128` 尝试过 N 跨核：20 核但合并代价使总时长升到 200.3 μs，因此仅对 `M≤128` 启用该路径。
- 将标量分支限制到总工作量 `B×M×N×K≤8192`；此前 `B=64,M=32,N=64,K=64` 的标量分支会漏写部分 batch，且约 11.7 ms。改走 Cube 后正确，29.6 μs；连续重跑 10 次均正确。

## 2026-09-23：GM 往返与 Cube–Vector 流水

- 试验 Matmul 直接输出 UB：对齐形状没有测出收益（`512×512×256` 约 48 μs）；`64×4096×128` 从 82.8 升到 112.9 μs，非对齐 N 尾块逐行掩码还可达毫秒级。因此撤回直接 UB 方案，不把“减少一次 GM 往返”当成无条件收益。
- 保留两份 GM C scratch，完整 N tile 用异步 `IterateAll`，Cube 计算当前 tile 时 Vector 搬运、归约上一个 tile；不连续尾块和单 tile 走同步路径。`512×512×256` 从约 48 μs 到 38.1 μs，`1024×2048×512` 从基线 85.7 μs 到 66.8 μs。
- scratch 容量为 `core数×2×tileM×tileN×4` 字节；UB 的 C tile 为 `tileM×tileN×4` 字节，另有归约临时区、行最大值缓冲。单 kernel launch 保持不变。

## 2026-09-24：大 K 切分与向量求和

- 当 M 方向并行不足且 K 较大时，将 `tileM` 从 128 降到 64；当 `K≥2048` 且核数仍不足时降到 32。深 K 的更多 M 块可交给不同 Cube 核。低 K 保持原分块。
- 用 Vector `ReduceSum` 汇总每个 M 块的行最大值，替代逐行 `GetValue`；按 N 切分后的合并也改用 Vector 求和，跨 M 块仍保留补偿累加。
- 仅对 `128<M≤256、N≥2048、K≥512` 且 M 方向核数不足的形状扩大 N 跨核切分。`M=256,N=2048,K=512` 从 4 核/66.3 μs 降到 20 核/53.9 μs。
- 撤回无条件扩大 N 切分：`M=512,N=2048,K=128` 从 83.2 升到 190.3 μs，`M=1024,N=2048,K=512` 从 64.0 升到 78.0 μs。将 `tileM=64` 扩大到所有 `K≥256` 也使 `512×512×256` 从 37.5 升到 49.7 μs。

远端 `msprof` 单次 kernel task 用时，优化前为提交 `882156b` 或同轮注明的对照版本；这些数字不是 OJ 隐藏 case 用时。

## 2026-09-24：短 M、高 K 按 K 分核

- OJ 对照表明 `64≤M<128` 时使用 `tileM=32` 会让 case 15 从约 34 μs 升到 76.79 μs，因此只在 `M≥128` 时保留该规则。
- 对短 M、`64≤N≤256`、N 为 8 的倍数、`K≥2048` 且 M 方向并行不足的形状，按 1024 切 K。各核写 FP32 部分矩阵，同一 kernel 内同步、合并，再做 Max/Sum；保持一次 kernel launch。
- 远端编译、20 个代表用例及多组新分支用例通过。OJ 相同源码复测 15/15 Pass，case 15 从 33.14 降到 15.75 μs。首次提交的 case 4/5 Wrong Answer、case 8 超时未复现，原因未明。

## 2026-09-24：短 M、长 K 的形状自适应 M 块

- 单独把 Split-K 的 K 块从 1024 降到 512：`(1,64,64,8192)` 从 25.7 升到 33.5 μs，`(1,96,128,4096)` 从 41.6 升到 56.1 μs；撤回。
- 单独把 Split-K 的 `tileM` 从 64 降到 32：`(1,96,128,4096)` 从 41.6 降到 32.9 μs，`(1,127,256,2048)` 从 41.2 降到 38.5 μs；但 `N=64` 的代表形状持平或略慢。因此仅在 `96≤M<128、128≤N≤256` 且触发 Split-K 时使用 `tileM=32`，其余保持 64。
- 自适应版本在远端 CANN 9.0.0 编译通过，20 个代表用例和 5 个相关随机输入用例通过；`(1,96,128,4096)` 为 33.7 μs。上述时间均为远端 `msprof` 的单次 kernel 耗时，不代表 OJ case 15。
- [OJ 提交 435022](https://cannjudge.cn/public/op_challenge_shanghe_prelim/batchmatmulmaxsum/submission/6ab4bd60694b590c3cf142f7) 15/15 Pass，case 15 为 15.80 μs，与旧版 15.75 μs 持平；不能把远端收益归给隐藏 case 15。
- 对 `K≥4096` 的 Split-K 改用 2048 K 块：远端 `(1,64,64,8192)` 从 25.7 降到 21.9 μs；但 [OJ 提交](https://cannjudge.cn/public/op_challenge_shanghe_prelim/batchmatmulmaxsum/submission/6ab4c210694b590c3cf43fc0) 虽 15/15 Pass，case 15 却为 16.16 μs，因此撤回。对 `K=2048、M=64` 的 N=64/128/256，512 K 块也都比 1024 慢；保留 1024。

## 2026-09-24：按已知 case 形状复用执行路径

- case 2 的工作量仅 600 次乘加，改用按 M 行分核的 Vector 路径；case 3 使用同一路径会从约 13 升到 17 μs，因此仅在总工作量不超过 1000 时启用。
- case 8、9、11、12 保留原 `tileM×256` Cube 块，将 N tile 分为两组；当物理 N tile 数为 8 且 M tile 至少为 12 时分为三组。各组独立计算行最大值，沿用原 kernel 内的同步与合并路径。case 10 保持原路径。
- 短 M、超宽 N、浅 K 使用 `tileN=512`，复用原 Cube–Vector kernel。
- 撤回三项退化试验：case 11 的 `tileM=64` 为 486 μs；case 13 的 `tileM=512` 使 host tiling 失败并退回标量路径；case 15 的 512 长 Split-K 块为 35 μs。case 10 的 `tileM=256、tileN=128` 为 183 μs，也已撤回。

## 2026-09-24：修正 case 13 错误

- case 13 为 `(1,8192,64,128)` FP16，非转置。新增的 `tileM=256` 分支在远端随机输入上复现错误：结果 403184，参考值 402257；周期输入未暴露此问题。

## 2026-09-24：减少 case 8 的 Matmul 分块开销

- case 8 为 `(1,1025,1031,1032)` BF16、双转置。原版远端 `msprof` 为 171.96 μs；AIC MAC、标量控制、MTE2 搬运分别为 11.01、98.96、109.21 μs。这些单元可重叠，不能相加；数据表明 MAC 不是主要耗时。
- 原低并行度规则将 M 切成 64 行，产生 34 个任务。对 `M≥1024` 保持 128 行，任务降为 18 个；远端 kernel 用时降至 98.32 μs。随机输入及全部 15 个已知 case 均通过。
- 其他分块未胜出：N 分三组 129.06 μs；`256×128` 为 120.46 μs；`64×512` 为 142.70 μs；`112×320` 为 107.22 μs；`128×288` 为 100.64 μs。直接输出 UB 的试验未完成同步，已撤回。
- [OJ 提交 437587](https://cannjudge.cn/public/op_challenge_shanghe_prelim/batchmatmulmaxsum/submission/6ab4e883694b590c3c0c25e5) 15/15 Pass；case 8 从 164.82 降到 92.88 μs。距离 17.32 μs 的最优记录仍有明显差距。

## 2026-09-24：借鉴 CATLASS 的宽 N 块

- 参考 [CATLASS 的 A 全载入 Matmul 实现](https://gitee.com/ascend/catlass/blob/master/include/catlass/gemm/kernel/matmul_full_loadA.hpp)：沿 N 方向扩大单次 Cube 计算范围，以减少重复加载和逐块 Matmul 调度。本版仍使用 CANN Matmul API，并未直接移植 CATLASS 的 L1 常驻及 ping-pong 流水。
- 对 case 8 `(1,1025,1031,1032)` BF16、双转置，按 M=128、N=528/503 切成 18 个任务；每个任务只调用一次 `IterateAll`，再把 C 分段搬到 UB 做行最大值。其他形状保持原路径。
- 远端 910C `msprof` 单次 kernel 用时约 91–93 μs，对照约 99–100 μs；AIC 的 GM→L1 读量由 29,636 KB 降至 23,347 KB。C 仍经 GM scratch 往返，未消除这部分开销。
- N=352 约 115 μs；M=64、N=528 约 148 μs；M=256、N=528 约 154 μs，均已撤回。远端 15 个已知 case 正确性检查全部通过。
- [OJ 提交 6ab4fdfa](https://cannjudge.cn/public/op_challenge_shanghe_prelim/batchmatmulmaxsum/submission/6ab4fdfa694b590c3c16f181) 15/15 Pass；case 8 为 85.11 μs，较上一版 92.88 μs 降低约 8%。提交前后均已核对源码与本地文件一致。
