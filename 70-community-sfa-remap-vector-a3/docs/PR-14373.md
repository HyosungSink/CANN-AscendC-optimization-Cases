## What changed

- add an Ascend C implementation of SFA DCP sparse-index remapping and stable compaction;
- route the SFA CP backend through the custom operator on NPU while retaining the existing reference behavior;
- fuse owner filtering, exact int32 DCP-local remapping, stable packing, and trailing `-1` fill into one AIV launch;
- use exact int32 shift/mask remapping for power-of-two production configurations;
- use exact Vector magic division for non-power-of-two DCP/interleave configurations instead of a Scalar fallback;
- process TopK rows in UB-sized chunks while preserving global row order and fixed-width output;
- support dynamic TopK through 8192 and add focused coverage for int32 precision and chunk boundaries.

## Why

`_remap_sparse_indices` runs once per SFA layer during DCP execution. The replaced path launches a multi-kernel PyTorch chain, converts int32 indices through float32, sorts packing keys, and gathers the result. This adds decode launch overhead, becomes expensive for the 8K-32K query-token rows used by chunked prefill, and loses integer precision above 16,777,216.

The fused operator preserves TopK order, dtype, fixed-width output shape, trailing `-1` padding, and exact int32 semantics while replacing the chain with one native launch. Wide rows remain on AIV and are processed in UB-sized chunks rather than falling back to a per-element Scalar loop.

The server-tokenized input-length vector was `[4262, 4287, 4292, 4239]` in every group, proving that the paired states used identical prompts. The nominal 4096-token generator input expands slightly after the model's server-side tokenization; this expansion is identical in all four groups. Output length was exactly 1000 for every request. Exact TPOT is calculated from the stored per-token timestamps as `(last timestamp - first-token timestamp) / output_tokens`; AISBench logs, timestamp databases, per-request JSON, service logs, manifests, and wall-clock files are retained.

Across the eight prompt-matched request pairs, the mean TPOT change was -4.33%, with a request-level bootstrap 95% CI of `[-4.98%, -3.68%]` (20,000 deterministic resamples). Every paired request improved; the individual changes ranged from -5.22% to -3.44%. This interval describes these eight repeated requests only.

The two final groups showed first-request TTFT outliers (2337.1 ms and 1889.9 ms), while their remaining six TTFT samples were 1499.0-1512.5 ms. Consequently, mean/P90 TTFT and combined prefill throughput regress, whereas median TTFT is unchanged. These cold-start samples are retained rather than discarded. Decode TPOT, E2EL, output throughput, benchmark duration, and wall time all improve despite those outliers.

The previous single-group result in this PR reported TPOT -3.54% and output throughput +3.65%. The fresh fixed-prompt ABBA run reports -4.33% and +4.12%, respectively. Absolute latency differs between runs, but the direction and magnitude of the end-to-end decode benefit are consistent.

## Does this PR introduce any user-facing change?

No. This is an internal performance optimization with unchanged operator output semantics and no new configuration or environment variable.
